Accidentally Pushing Credentials to GitHub: A Technical Post-Mortem

Ehmad February 15, 2026 10 min read

A Deep Dive into Git Secret Exposure, Recovery, and Prevention

The Incident

A production environment’s .env file containing sensitive credentials was accidentally committed and pushed to a public GitHub repository. What seemed like a straightforward fix quickly escalated into a multi-layered incident affecting production services and requiring coordinated remediation across multiple systems.

This post-mortem examines the technical details, cascading failures, and systemic improvements needed to prevent similar incidents.

What Went Wrong

Primary Failure: Missing .gitignore Entry

The root cause was deceptively simple—the .env file wasn’t excluded from version control. Despite being a well-known best practice, this configuration gap allowed sensitive credentials to enter the repository.

Exposed Data:

  • Database connection strings and passwords
  • API authentication keys
  • JWT signing secrets
  • Third-party service tokens

Secondary Failure: Template File Contamination

During remediation efforts, a second exposure was discovered: the .env.example file contained actual production credentials instead of placeholder values. This meant two separate files in the repository history contained live credentials.

Tertiary Failure: Deployment Hook Design

The production deployment system used a post-receive Git hook with this critical line:

git --work-tree=$TARGET --git-dir=$GIT_DIR checkout -f $BRANCH

The -f flag force-overwrites the working directory. When data files were removed from Git tracking during cleanup, the deployment hook deleted them from production, causing service disruption.

The Recovery Process

Phase 1: Immediate Credential Rotation (Priority One)

The first action was rotating all exposed credentials:

  • Database passwords regenerated
  • API keys revoked and replaced
  • JWT secrets rotated
  • Service authentication tokens refreshed

Critical Insight: Removing files from Git doesn’t remove credentials from the internet. Any exposed secret must be treated as permanently compromised, regardless of how quickly it’s removed from the repository.

Phase 2: History Rewriting

Removing the current file isn’t enough—the credentials exist in every commit where they appeared. Git’s immutable history means they’re accessible through:

  • Commit history (git log)
  • GitHub’s cached views
  • Search engine indexing
  • Third-party Git mirrors

Tool Selection: git-filter-repo

While several tools can rewrite Git history, git-filter-repo was chosen for its safety features and performance:

# Installation
pip install git-filter-repo

# Remove sensitive files from entire history
git-filter-repo --path .env --invert-paths --force
git-filter-repo --path .env.example --invert-paths --force

Critical Gotcha: git-filter-repo removes all remotes as a safety measure to prevent accidental pushes. Remotes must be manually re-added before pushing.

Phase 3: Multi-Remote Coordination

The repository had two remotes:

  • origin - GitHub (public)
  • production - Bare repository on production server

History rewriting had to be coordinated across both:

# Re-add remotes after filter-repo
git remote add origin :user/repo.git
git remote add production user@server:~/repo.git

# Force push to both
git push --force origin --all
git push --force production --all

Phase 4: Production Data Recovery

The deployment triggered by the force push exposed a critical flaw in the deployment hook. Production data files that were removed from Git tracking were also deleted from the filesystem.

Files Lost:

  • known_devices.json - Device tracking database
  • device_database.json - Device metadata
  • debug.log - Application logs
  • blacklisted.json - Security blocklist
  • requests.json - Request history

Recovery Method:

These files still existed in Git history before cleanup. They were restored using:

# Find the last commit containing the files
git log --all --oneline -- known_devices.json | head -1

# Restore from that commit
git checkout <commit-hash> -- known_devices.json device_database.json debug.log blacklisted.json requests.json

# Fix permissions
chown www-data:www-data *.json *.log
chmod 644 *.json *.log

Phase 5: Deployment Hook Remediation

The post-receive hook was rewritten to preserve untracked files during deployment:

#!/bin/bash
TARGET="/var/www/app"
GIT_DIR="$HOME/app.git"
BRANCH="main"

while read oldrev newrev ref
do
  if [[ $ref = refs/heads/$BRANCH ]]; then
    echo "Deploying to production..."
    
    # Backup data files before checkout
    cd $TARGET
    cp -f known_devices.json known_devices.json.bak 2>/dev/null || true
    cp -f device_database.json device_database.json.bak 2>/dev/null || true
    cp -f debug.log debug.log.bak 2>/dev/null || true
    cp -f blacklisted.json blacklisted.json.bak 2>/dev/null || true
    cp -f requests.json requests.json.bak 2>/dev/null || true
    
    # Deploy code
    git --work-tree=$TARGET --git-dir=$GIT_DIR checkout -f $BRANCH
    
    # Restore data files if deleted by checkout
    [ ! -f known_devices.json ] && mv -f known_devices.json.bak known_devices.json 2>/dev/null || true
    [ ! -f device_database.json ] && mv -f device_database.json.bak device_database.json 2>/dev/null || true
    [ ! -f debug.log ] && mv -f debug.log.bak debug.log 2>/dev/null || true
    [ ! -f blacklisted.json ] && mv -f blacklisted.json.bak blacklisted.json 2>/dev/null || true
    [ ! -f requests.json ] && mv -f requests.json.bak requests.json 2>/dev/null || true
    
    # Cleanup
    rm -f *.bak
    
    # Fix permissions
    chown www-data:www-data $TARGET/*.json $TARGET/*.log 2>/dev/null || true
    chmod 644 $TARGET/*.json $TARGET/*.log 2>/dev/null || true
    chown www-data:www-data $TARGET/.env 2>/dev/null || true
    chmod 600 $TARGET/.env 2>/dev/null || true
    
    echo "Deployment complete!"
  fi
done

Technical Lessons

1. Git History Is Immutable (Until It Isn’t)

Git’s design philosophy treats history as immutable, which is excellent for collaboration but catastrophic for secrets. Once committed, credentials are:

  • Permanently in history until explicitly removed
  • Replicated to all clones
  • Potentially cached by GitHub
  • Possibly indexed by search engines

The Fix: History rewriting is possible but destructive. It changes all commit hashes, breaks existing clones, and requires force-pushing—a coordinated operation that can’t be done quietly.

2. .gitignore Is Not Retroactive

Adding .env to .gitignore after it’s been committed does nothing. The file remains in history. .gitignore only affects future operations.

Correct Workflow:

# Add to .gitignore FIRST
echo ".env" >> .gitignore
git add .gitignore
git commit -m "ignore environment files"

# THEN create .env
touch .env
# File is now ignored

3. Template Files Need Sanitization

.env.example files serve as templates for other developers. They should contain:

# WRONG - Real credentials
DB_PASSWORD=MyActualPassword123
API_KEY=sk_live_abc123xyz789

# RIGHT - Placeholders
DB_PASSWORD=your_secure_password_here
API_KEY=your_api_key_here

4. Deployment Hooks Must Account for State

Git tracks code, not state. Production systems often have files that shouldn’t be in Git:

  • User-uploaded content
  • Generated caches
  • Runtime logs
  • Session data
  • Application-managed databases

Deployment scripts that blindly overwrite the working directory will destroy this state.

Better Approaches:

Option A: Separate state directory

/var/www/app/        # Git-managed code
/var/www/app-data/   # Application state

Option B: Explicit exclusions

# Only checkout tracked files, preserve untracked
git checkout -f $BRANCH

Option C: Backup and restore (shown above)

5. Multi-Remote Force Push Coordination

When pushing to multiple remotes, history must be synchronized:

# This creates divergent histories (BAD)
git push --force origin main
# Make more changes
git push --force production main

# This keeps them synchronized (GOOD)
git push --force origin main
git push --force production main
# Both remotes now have identical history

6. File Ownership in Deployment Hooks

The deployment hook runs as the SSH user, but web files need different ownership:

# Wrong - Files owned by deployment user
git checkout -f $BRANCH

# Right - Explicitly set ownership
git checkout -f $BRANCH
chown -R www-data:www-data $TARGET

Prevention Strategy

Layer 1: Pre-Commit Prevention

Git Hooks:

Create .git/hooks/pre-commit:

#!/bin/bash
if git diff --cached --name-only | grep -E '^\.env$|^\.env\..*'; then
    echo "Error: Attempting to commit .env file"
    echo "Add to .gitignore instead"
    exit 1
fi

Make executable:

chmod +x .git/hooks/pre-commit

Automated Tools:

  • git-secrets - Scans for patterns matching credentials
  • detect-secrets - Pre-commit hook for secret detection
  • gitleaks - SAST tool for hardcoded secrets

Layer 2: Repository Configuration

Comprehensive .gitignore:

# Environment files
.env
.env.*
!.env.example

# Application state
*.log
*.json
!package.json
!composer.json

# Server configuration
.htaccess
php.ini

# Uploads
uploads/
storage/

# Caches
cache/
tmp/

Branch Protection:

Enable on GitHub:

  • Require pull request reviews
  • Require status checks
  • Restrict force pushes
  • Require signed commits

Layer 3: Secrets Management

Never Store Secrets in Git:

Use dedicated secret management:

  • HashiCorp Vault - Enterprise secret storage
  • AWS Secrets Manager - Cloud-native secrets
  • Azure Key Vault - Microsoft ecosystem
  • Google Secret Manager - GCP integration

Environment Variable Injection:

# Deploy-time injection
export DB_PASSWORD=$(vault read -field=password secret/db)
php artisan serve

Layer 4: Monitoring and Detection

GitHub Scanning:

  • Enable GitHub secret scanning (free for public repos)
  • Configure custom patterns for proprietary secrets
  • Set up notifications for detected secrets

Audit Logging:

Monitor for:

  • Unexpected credential usage from new IPs
  • API key usage spikes
  • Failed authentication attempts
  • Credential rotation events

Layer 5: Incident Response Preparation

Runbook for Credential Exposure:

  1. Immediate (0-5 minutes)

    • Rotate all exposed credentials
    • Verify rotation completed successfully
    • Monitor for unauthorized access

  2. Short-term (5-30 minutes)

    • Assess scope of exposure
    • Check logs for credential usage
    • Notify stakeholders if needed

  3. Medium-term (30 minutes - 2 hours)

    • Remove from Git history
    • Force push to all remotes
    • Verify removal from GitHub cache

  4. Long-term (2+ hours)

    • Review security logs for 30 days
    • Conduct post-mortem
    • Implement additional controls

Architecture Improvements

Separate Deployment from State

Before:

/var/www/app/
├── .env                  # Mixed: config
├── index.php             # Deployed: code
├── dashboard.php         # Deployed: code
├── known_devices.json    # State: data
└── requests.json         # State: data

After:

/var/www/app/             # Git-deployed code only
├── index.php
├── dashboard.php
└── includes/

/var/www/app-config/      # Server-managed config
├── .env
└── config.php

/var/www/app-data/        # Application state
├── known_devices.json
├── requests.json
└── logs/

Update application to load from separate paths:

// Load config from separate directory
$dotenv = Dotenv\Dotenv::createImmutable('/var/www/app-config');
$dotenv->load();

// Store data in separate directory
$dataPath = '/var/www/app-data/';

Production-Only Files Strategy

For files that must exist in production but not GitHub:

Option A: Template + Manual Creation

# In repo: .env.example
DB_HOST=localhost
DB_NAME=database_name
DB_PASSWORD=your_password_here

# On server: Copy and fill
cp .env.example .env
nano .env  # Fill with real values

Option B: Injection Script

#!/bin/bash
# deploy-inject-config.sh

# Create .env from secure storage
cat > /var/www/app/.env << EOF
DB_HOST=$(vault read -field=host secret/db)
DB_NAME=$(vault read -field=name secret/db)
DB_PASSWORD=$(vault read -field=password secret/db)
EOF

chmod 600 /var/www/app/.env
chown www-data:www-data /var/www/app/.env

Add to post-receive hook:

# After checkout
git --work-tree=$TARGET --git-dir=$GIT_DIR checkout -f $BRANCH

# Inject config
bash $HOME/deploy-inject-config.sh

The Cost of This Incident

Time Investment

  • Detection to rotation: 10 minutes
  • Total remediation: 60 minutes
  • Documentation: 120 minutes
  • Process improvements: 180 minutes

Total: ~6 hours of engineering time

Service Impact

  • Downtime: 60 minutes
  • Degraded service: 30 minutes
  • User impact: All production users

Security Impact

  • Credential exposure window: 15-30 minutes
  • Rotation completed: Yes
  • Unauthorized access detected: No
  • Long-term monitoring: Ongoing

Key Takeaways

  1. Secrets in Git are permanently exposed - History rewriting is complex, risky, and doesn’t guarantee the secret wasn’t already harvested.

  2. Credential rotation is non-negotiable - Even if you remove credentials from Git in 30 seconds, treat them as compromised.

  3. Deployment automation needs safety rails - Hooks that blindly overwrite filesystems will eventually destroy production state.

  4. Prevention is cheaper than remediation - A pre-commit hook takes 5 minutes to implement; this incident consumed 6 hours.

  5. Template files need the same security rigor - .env.example with real credentials is just as dangerous as .env.

  6. Multi-layer security is essential - No single control prevents this incident. Pre-commit hooks, .gitignore, secret scanning, and proper architecture all contribute.

  7. State and code should be separated - Mixing deployed code with runtime state creates deployment complexity and data loss risks.

  8. Force push operations require planning - When rewriting history across multiple remotes, coordination prevents divergent histories and lost work.

Conclusion

This incident demonstrates how a simple configuration oversight can cascade into a complex, multi-system remediation effort. The mistake wasn’t just committing the .env file—it was the absence of defensive layers that would have prevented or quickly caught the error.

Modern development requires defense in depth:

  • Prevent: Pre-commit hooks, gitignore templates, secret scanning
  • Detect: GitHub secret scanning, audit logs, monitoring
  • Respond: Runbooks, rotation procedures, communication plans
  • Recover: Backup strategies, deployment safety, state management

The best incident is the one that never happens. Invest in prevention now, because credential rotation at 2 AM is significantly more expensive than a 5-minute pre-commit hook setup.
