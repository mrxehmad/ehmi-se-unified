Fixing Traefik v3 Encoded Character Blocking with Pi-hole

Ehmad December 25, 2025 6 min read

If you’re running Pi-hole behind Traefik v3 as a reverse proxy, you may encounter a frustrating error when trying to manage regex-based domain blocking rules. The Pi-hole web interface returns a 400 Bad Request error, and your Traefik logs show messages like:

Rejecting request because it contains encoded character %5C in the URL path: /api/domains/deny/regex/(%5E%7C%5C.)(cn)%24
Rejecting request because it contains encoded character %3F in the URL path: /api/domains/deny/regex/(%3Fi)vpn

This happens when you try to enable, disable, or modify domain groups that contain regex patterns in Pi-hole’s admin interface.

Why Does This Happen?

Traefik v3 introduced a security feature that blocks HTTP requests containing certain URL-encoded characters in the path. This is designed to prevent path traversal attacks and other security vulnerabilities. The blocked characters include:

  • %2F - Forward slash (/)
  • %5C - Backslash ()
  • %00 - Null character
  • %3B - Semicolon (;)
  • %25 - Percent (%)
  • %3F - Question mark (?)
  • %23 - Hash (#)

Pi-hole’s API uses regex patterns for domain blocking, and these patterns often contain special characters like (?i) for case-insensitive matching or \. for literal dots. When the Pi-hole web interface sends these patterns to the API, they’re URL-encoded (e.g., \ becomes %5C, ? becomes %3F).

Traefik v3 sees these encoded characters and rejects the request before it even reaches Pi-hole, resulting in the 400 error.

The Investigation

The issue becomes clear when comparing direct access to Pi-hole versus access through Traefik:

Works (Direct HTTP access):

curl 'http://10.1.15.10:8000/api/domains/deny/regex/(%5E%7C%5C.)(cn)%24' \
  -X PUT \
  -H 'Content-Type: application/json' \
  --data-raw '{"groups":[0,1,2,3],"comment":"cn stuff","enabled":true,"type":"deny","kind":"regex"}'

Fails (Through Traefik HTTPS):

curl 'https://pihole.example.com/api/domains/deny/regex/(%5E%7C%5C.)(cn)%24' \
  -X PUT \
  -H 'Content-Type: application/json' \
  --data-raw '{"groups":[0,1,2,3],"comment":"cn stuff","enabled":true,"type":"deny","kind":"regex"}'

The URL encoding is identical in both cases, confirming that Traefik is the culprit, not the client or Pi-hole.

The Solution

Traefik v3.2 and later versions include configuration options to allow specific encoded characters. You need to modify your Traefik static configuration file.

Step 1: Update Your traefik.yaml

Add the encodedCharacters configuration under your HTTPS entrypoint. This configuration was introduced in Traefik v3.2 and allows you to selectively permit encoded characters in URL paths.

Reference: Traefik Documentation - Request Path

entryPoints:
  web:
    address: ":80"
  websecure:
    address: ":443"
    http3: {}
    http:
      encodedCharacters:
        allowEncodedSlash: true          # %2F - Forward slash
        allowEncodedBackSlash: true      # %5C - Backslash (Required for Pi-hole)
        allowEncodedNullCharacter: true  # %00 - Null character
        allowEncodedSemicolon: true      # %3B - Semicolon
        allowEncodedPercent: true        # %25 - Percent sign
        allowEncodedQuestionMark: true   # %3F - Question mark (Required for Pi-hole)
        allowEncodedHash: true           # %23 - Hash/pound sign

api:
  dashboard: true
  insecure: true

providers:
  docker:
    exposedByDefault: false
  file:
    directory: /etc/traefik/dynamic
    watch: true

certificatesResolvers:
  cloudflare:
    acme:
      email: 
      storage: /letsencrypt/acme.json
      dnsChallenge:
        provider: cloudflare
        delayBeforeCheck: 90
        resolvers:
          - "1.1.1.1:53"
          - "1.0.0.1:53"

log:
  level: INFO

Important: The most critical settings for Pi-hole are:

  • allowEncodedBackSlash: true - Required for \ in regex patterns
  • allowEncodedQuestionMark: true - Required for ? in regex patterns like (?i)

All seven encoded character options are needed to fully support Pi-hole’s regex functionality.

Step 2: Verify Your Pi-hole Dynamic Configuration

Your Pi-hole dynamic configuration (pihole.yaml) should remain simple:

http:
  middlewares:
    https-redirect:
      redirectScheme:
        scheme: https
        permanent: true

  routers:
    pihole-redirect:
      rule: "Host(`pihole.example.com`)"
      entryPoints:
        - web
      middlewares:
        - https-redirect
      service: noop@internal
    
    pihole:
      rule: "Host(`pihole.example.com`)"
      entryPoints:
        - websecure
      service: pihole
      tls:
        certResolver: cloudflare

  services:
    pihole:
      loadBalancer:
        servers:
          - url: "http://pihole:80"

Step 3: Apply the Changes

Restart Traefik to apply the new configuration:

docker restart traefik

Or if using docker-compose:

docker-compose restart traefik

Step 4: Verify the Fix

Check your Traefik logs to ensure the rejection messages are gone:

docker logs traefik -f

You should no longer see messages like “Rejecting request because it contains encoded character”.

Test by trying to enable or disable a regex domain rule in Pi-hole’s web interface. It should now work without errors.

Important Security Considerations

Allowing encoded characters reduces some of Traefik’s built-in security protections against path traversal and injection attacks. Consider these points:

  1. Understand the risks: Each allowed character opens a potential attack vector if your backend doesn’t properly validate input
  2. Pi-hole validation: Pi-hole validates regex patterns, but ensure you’re running the latest version with security patches
  3. Network segmentation: Keep your Pi-hole and Traefik on a trusted internal network, not directly exposed to the internet
  4. Monitor logs: Regularly check Traefik and Pi-hole logs for suspicious activity
  5. Regular updates: Keep both Traefik and Pi-hole updated to the latest versions
  6. Alternative approach: If security is paramount, consider using the separate entrypoint method (see Alternative Solutions below) to limit the scope of allowed encoded characters

Alternative Solutions

If you prefer not to allow encoded characters globally, here are alternatives:

Option 1: Create a Separate Entrypoint for Pi-hole

entryPoints:
  web:
    address: ":80"
  websecure:
    address: ":443"
    http3: {}
  pihole-secure:
    address: ":8443"
    http3: {}
    http:
      encodedCharacters:
        allowEncodedBackSlash: true
        allowEncodedQuestionMark: true

Then update your Pi-hole router to use pihole-secure entrypoint and access Pi-hole at https://pihole.example.com:8443.

Option 2: Use Nginx as an Intermediary

Place an Nginx container between Traefik and Pi-hole:

server {
    listen 8080;
    location / {
        proxy_pass http://pihole:80;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Point Traefik to Nginx instead of directly to Pi-hole.

Option 3: Downgrade to Traefik v2

Traefik v2.11 doesn’t have this encoded character restriction and works with Pi-hole out of the box:

services:
  traefik:
    image: traefik:v2.11

Common Pitfalls

YAML Indentation Errors

YAML is strict about indentation. Use spaces, not tabs. The http: section must be properly indented under websecure::

websecure:
  address: ":443"
  http3: {}
  http:              # Two spaces
    encodedCharacters: # Four spaces
      allowEncodedBackSlash: true # Six spaces

Configuration Not Loading

If you see “field not found, node: encodedPath” errors, you’re using an older Traefik version or incorrect syntax. The encodedCharacters configuration was introduced in Traefik v3.2. Check your version:

docker exec traefik traefik version

Changes Not Taking Effect

After modifying traefik.yaml, you must restart Traefik. Simply reloading dynamic configuration isn’t enough for static configuration changes.

Testing Your Configuration

After applying the fix, test with a real curl command:

curl 'https://pihole.example.com/api/domains/deny/regex/(%3Fi)vpn' \
  -X PUT \
  -H 'Content-Type: application/json; charset=UTF-8' \
  -H 'Cookie: sid=YOUR_SESSION_ID' \
  -H 'X-CSRF-TOKEN: YOUR_CSRF_TOKEN' \
  --data-raw '{"groups":[0],"comment":"test","enabled":false,"type":"deny","kind":"regex"}'

A successful response (200 OK) indicates the fix is working.

Conclusion

The encoded character blocking in Traefik v3 is a security feature that can interfere with legitimate applications like Pi-hole that use special characters in their API paths. By carefully configuring the encodedCharacters settings in your Traefik static configuration, you can allow Pi-hole to function properly while maintaining reasonable security.

Remember to only enable the specific encoded characters you need, keep your systems updated, and ensure your backend applications properly validate input.
