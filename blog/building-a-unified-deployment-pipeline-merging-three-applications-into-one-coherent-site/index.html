Building a Unified Deployment Pipeline: Merging Three Applications into One Coherent Site

Ehmad November 29, 2025 5 min read

This article documents the architectural decisions and implementation strategies employed in consolidating three distinct web applications. a Next.js portfolio, a React-based tools suite, and a Publii blog into a unified deployment pipeline. The solution leverages GitHub Actions for automated builds, Git submodules for modular component management, and Cloudflare Pages for hosting, whilst maintaining separation of concerns and independent development workflows.

1. Introduction

Modern web development often necessitates the integration of multiple applications under a single domain, presenting unique challenges in build orchestration, routing, and deployment. This project addresses these challenges by implementing a streamlined continuous deployment workflow that preserves the autonomy of individual components whilst presenting them as a cohesive user experience.

1.1 Project Structure

The architecture comprises three principal components:

  • Portfolio (/): A Next.js application serving as the primary landing page and professional showcase
  • Tools (/tools): A React single-page application providing utility features
  • Blog (/blog): A Publii-generated static blog with independent content management

2. Technical Implementation

2.1 Repository Architecture

The project employs Git submodules to maintain independent repositories for each component, allowing for:

  • Isolated version control and commit history
  • Independent development cycles
  • Simplified testing and debugging
  • Clear separation of concerns
main-site/
├── portfolio/      (submodule)
├── tools/          (submodule)
└── blog/           (submodule, blog branch)

2.2 Build Pipeline

The deployment workflow, triggered manually via GitHub Actions, executes the following sequence:

  1. Checkout Phase: Retrieves all repositories with their submodules, ensuring the blog submodule switches to its dedicated blog branch
  2. Build Phase: Compiles both Node.js applications independently, with the tools application configured for a /tools base path
  3. Integration Phase: Constructs a unified directory structure by copying built assets to their respective paths
  4. Deployment Phase: Commits the compiled assets to a production branch, ready for hosting

2.3 Routing and Configuration

Three critical configuration files manage site behaviour:

robots.txt: Directs search engine crawlers to appropriate sitemaps for each section

sitemap.xml: Provides a sitemap index coordinating discovery across all three applications

_redirects: Handles legacy subdomain redirects and single-page application routing for the tools section

3. Key Design Decisions

3.1 Submodule Strategy

Rather than employing a monorepo approach, Git submodules were selected for their ability to maintain truly independent repositories. This proves particularly valuable when components require different deployment schedules or have distinct contributor teams.

3.2 Build-Then-Deploy Pattern

The workflow performs all compilation in the CI environment rather than on the hosting platform. This approach offers several advantages:

  • Predictability: Builds occur in a controlled environment with consistent dependencies
  • Flexibility: Different build tools and Node versions can be employed per component
  • Speed: The hosting platform simply serves pre-built assets without compilation overhead
  • Security: Build secrets and dependencies remain within the CI environment

3.3 Branch-Based Deployment

Deploying to a dedicated production branch, rather than directly to main, provides:

  • Clean separation between source code and compiled assets
  • Simplified hosting configuration (point to branch root)
  • Ability to inspect deployed assets independently
  • Protection of source branches from build artifacts

4. Challenges and Solutions

4.1 SPA Routing

Single-page applications like the React tools require special routing considerations. The _redirects file instructs Cloudflare Pages to serve index.html for all /tools/* paths, enabling client-side routing whilst avoiding 404 errors.

4.2 Blog Branch Management

The blog submodule maintains content on a separate blog branch to distinguish between Publii’s generated output and its configuration files. The workflow explicitly checks out this branch, ensuring the correct content is deployed.

4.3 Path Consistency

React’s build process required configuration via the PUBLIC_URL environment variable to ensure asset paths reference /tools rather than the root. This prevents broken links and ensures proper resource loading.

5. Recommendations and Best Practices

5.1 For Similar Projects

If you’re considering a similar architecture, I’d advise:

  • Start Simple: Begin with manual deployment to understand the full picture before automating
  • Test Independently: Ensure each component builds and runs correctly in isolation before integration
  • Document Paths: Maintain clear documentation of which files live where, particularly when using submodules
  • Version Lock: Pin Node versions and major dependencies to avoid unexpected build failures

5.2 Potential Improvements

Whilst the current solution proves effective, several enhancements could be considered:

  • Automated Testing: Integrate end-to-end tests before deployment to catch broken links or routing issues
  • Preview Deployments: Implement branch-based preview deployments for testing changes before production
  • Cache Optimisation: Investigate caching strategies to reduce build times for unchanged components
  • Monitoring: Add deployment notifications and uptime monitoring

5.3 When Not to Use This Approach

This architecture may not suit all scenarios. Consider alternatives if:

  • Components require frequent coordinated updates (a monorepo might be preferable)
  • Your team lacks familiarity with Git submodules (they can be tricky)
  • You need server-side rendering or dynamic routes (static hosting has limitations)
  • Build times become prohibitive (incremental builds might be necessary)

6. Conclusion

This unified deployment pipeline successfully consolidates three independent applications whilst preserving their modularity and independence. The solution demonstrates that with careful planning and appropriate tooling, complex multi-application sites can be managed through automated workflows without sacrificing simplicity or maintainability.

The key takeaway is that modern deployment needn’t be monolithic. By combining Git submodules, GitHub Actions, and intelligent routing configuration, we can achieve the best of both worlds: the organisational benefits of separate repositories with the user experience of a unified site.

The complete workflow requires minimal ongoing maintenance. simply trigger the action when updates are ready, and the pipeline handles the rest. It’s rather elegant in its simplicity, really.

Technical Stack: Next.js, React, Publii, GitHub Actions, Cloudflare Pages
Repository Structure: Git submodules with independent version control
Deployment Target: Static hosting with SPA routing support
Build Time: Approximately 3-5 minutes for full deployment
